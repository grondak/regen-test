# Session 20 — Network boundaries, partial failure and coupling

**Repo support:** Partly. No failure-injection material exists, but the pieces from sessions 6–19 are what you break, and local mode (`bash deploy/local/run_local.sh`, stage 20) lets you break each piece on a laptop.

**Concept (20 min):** network boundaries, latency, partial failure, timeout, retry, coupling, state. Keep theory attached to TinyWMS.
**Demo (20 min):** draw their actual system and kill or break components one at a time.

## 10 bullets to work from
1. Draw the real system on the whiteboard together, left to right: browser → API Gateway → Lambda → RDS, then Lambda → SQS → worker → ticket file, and Lambda → EventBridge → subscribers. Mark every arrow that crosses a network. Use `20-final-walkthrough/docs/end-to-end.md` as the answer key.
2. A local function call fails together with its caller. A network call can fail on its own: refused, timed out, or succeeded but the reply was lost. The caller cannot tell the last two apart.
3. Latency adds up: each hop costs time, and the user waits for the slowest synchronous chain. Which hops does the browser wait for? (Everything up to the database commit.) Which does it not? (Queue, worker, subscribers.)
4. Break 1: stop the server (session 6) while the page is open. Show the page's error text from session 9. Failing loudly beats failing silently.
5. Break 2: take away the database. In local mode (`cd "$TINYWMS/20-final-walkthrough" && bash deploy/local/run_local.sh --reset`), stop the server, `chmod a-r local-aws/tinywms.db` (or move the file), restart without `--reset`, and reload the page. Ask what the user sees (the page shows the failure, the server answers 500). In AWS the equivalent is stopping the instance or changing the security group (session 8).
6. Break 3, the partial failure to dwell on: the order commits, then the queue send fails. Reproduce it locally: with the system running and the folder `local-aws/pick-work` present, run `chmod a-w local-aws/pick-work` and submit an order. The page reports an error (HTTP 500 `PermissionError`), **but** the stock dropped and `sqlite3 local-aws/tinywms.db "select * from orders"` shows the order. No pick request was sent. Undo with `chmod u+w local-aws/pick-work`. In AWS you get the same thing by removing `sqs:SendMessage` from the Lambda role. Which component knows? Which should? Discuss retry, a dead-letter queue, and an outbox table as ideas, not as things the repo already has.
7. Break 4: kill the worker (`pkill -f pick_ticket_worker`; `run_local.sh` does not restart it, systemd would). Orders keep succeeding, message files pile up in `local-aws/pick-work`, and nothing is lost. The queue buys decoupling in time. Restart it with `python3 -m src.pick_ticket_worker local-aws/pick-work pick-tickets.txt --state-file local-aws/pick-ticket-worker-state.json --wait-time-seconds 2` (with `TINYWMS_LOCAL=1` exported) and watch it drain and write the tickets.
8. Timeouts and retries: a retry is only safe if the operation is idempotent. Submit the same order twice: the stage-11 file-backed server accepts it twice, local mode rejects the second with 409. Either way, see why a retry needs an ID; this sets up session 23.
9. Coupling: what does the order function need to know about the worker? Almost nothing, just the queue. What does it know about the event subscribers? Nothing at all. Contrast with the synchronous path, where it needs the database to be up.
10. Close with a table students fill in: for each component, "what if it is down", "what if it is slow", "who finds out", "is any data lost?". Keep it; they use it again in the final synthesis session.
